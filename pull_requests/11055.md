# wallet2: honor max_blocks bound during fast_refresh hash pulls
author: woodser
created_at: 2026-08-06T01:41:05Z
status: merged

Currently, monero-wallet-rpc cannot report any sync progress during the hash skip phase of wallet syncing, and because it's single-threaded, it cannot respond to any call during this phase. As a result, when restoring a wallet from a previous height, the wallet can be completely unresponsive for 3+ minutes during the hash skip phase. Even for newer wallets, the delay before reporting any sync progress is noticeable and significant.

Applications like Haveno will timeout after several minutes of no observed sync progress and attempt to connect to another monerod, which will run into the same problem again. So this is a real blocker to restore old wallets through the official API or native bindings to wallet2.

The official GUI does not suffer this problem because wallet_api refreshes on a dedicated thread and reads heights in process. As a result, restoring an old wallet in the official Monero GUI starts reporting sync progress immediately and responsively.

monero-wallet-rpc already has a constant to improve this, [`REFRESH_INDICATIVE_BLOCK_CHUNK_SIZE = 256`](https://github.com/monero-project/monero/blob/1bf1dff4be4b2a604fd761b532e1c5aff4cc0bad/src/wallet/wallet_rpc_server.cpp#L63), with a comment "just to split refresh in separate calls to play nicer with other threads". However, wallet2 ignores this bound within `fast_refresh` during the hash skip phase.

This PR makes it so that wallet2 honors the bound, so that when `refresh` is called with capped `max_blocks`, the internal `fast_refresh` is also capped with a maximum pulls per refresh. When the budget is hit, progress is reported via `blocks_fetched` and it returns, then the next call will resume where it left off. Unbounded callers (refresh RPC, simplewallet, wallet_api) pass no bound and are unchanged (max pulls = 0).

I've tested and verified that this PR allows wallets to report sync progress with the same immediate responsiveness as the official Monero GUI, whether by RPC or directly with native bindings, significantly improving the user experience. Without this PR, the user sees a substantial delay before any sync progress is reported (3+ minutes for older wallets), while with this PR, sync progress starts to be reported immediately. I've been running this fix in Haveno's RPC and native libs and observe the same immediate responsiveness as with the official GUI.

This PR ships with `MAX_HASH_PULLS_PER_REFRESH = 3` (~30k hashes per call) as a grounded starting point, but it could be tuned or derived from `max_blocks`.
