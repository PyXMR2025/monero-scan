# blockchain_db: resume interrupted pruning
author: Ap4sh
created_at: 2026-08-07T23:40:44Z
status: open

`pruning_seed` is committed at the first pruning checkpoint, so an interruption after that point makes the next startup take the incremental path and skip the unfinished historical scan

this stores the last processed transaction hash in the same LMDB transaction as each checkpoint, resumes after it on the next run, and clears the marker with the final commit. resumed operations also process newly matured tip records before continuing the historical scan

this protects pruning runs interrupted after this change. databases already interrupted by an older binary have no progress marker and can't be distinguished from completed databases without a full historical scan; the existing runtime `prune_blockchain` command remains the recovery path for those databases

related to #10178

tests:
- full unit suite with GCC 14.2
- `BlockchainDBTest/0.ResumeInterruptedPruning`
- verified the regression test fails if resume falls back to `MDB_FIRST`
