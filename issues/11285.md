# Bug: monerod cannot correctly identify database corruption caused by truncation
author: EntropyHoover
created_at: 2026-09-10T07:54:24Z
status: closed

This bug has previously been mentioned by issue 11117. https://github.com/monero-project/monero/issues/11117

The bug is caused by file system corruption due to abnormal program termination or power loss. It can be reliably reproduced by killing the vm that is running the initial sync of monero. When the system loses power, some writing of db still exists in ram and did not get transferred into disk. In this case the actual physical database contains less blocks than the metadata claims. The metadata block height is higher than the actual physical storage block height.

LMDB mapped data into virtual memory of the process, during the initialization the HardFork::init() will scan the recent blocks for reconstructing the state machine, and it will eventually request the block that actually did not exist on disk. The code will run and attempt to access non-existent data, then a SIGBUS error will be triggered, indicating that virtual ram page does not map to any disk file. 

```bash
./monerod --data-dir ~/crashDB/
2026-09-10 07:45:46.669	I Monero 'Fluorine Fermi' (v0.18.5.1-release)
2026-09-10 07:45:46.669	I Initializing cryptonote protocol...
2026-09-10 07:45:46.669	I Cryptonote protocol initialized OK
2026-09-10 07:45:46.669	I Initializing core...
2026-09-10 07:45:46.669	I Loading blockchain from folder /home/user/crashDB/lmdb ...
Bus error                  (core dumped) ./monerod --data-dir ~/crashDB/
```

Currently monero cannot handle the error, and will not display any information about the database corruption. The best way to avoid this is simply add a size check for the database, compare the actual physical size of db with the claimed page * page size. If the physical size is smaller, it indicates the database is corrupted.
