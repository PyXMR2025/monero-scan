# Linux: inactivity lock loops on password prompt and never unlocks (correct password ignored)

This only happens on Linux for me. On Windows inactivity lock is disabled anyway, so I can't compare 1:1.

Related / possibly the same class of bug: #5922, #9258. Also hard to escape from the lock prompt (#6192 / similar).

### Steps to reproduce

1. Open a wallet with `monero-wallet-cli` on Linux in a normal terminal (or under tmux/screen — see notes).
2. Leave it idle until inactivity lock kicks in (default is 90s), or wait for:
   `Locked due to inactivity. The wallet password is required to unlock the console.`
3. Type the correct wallet password and press Enter.
4. Observe: instead of returning to the `[wallet ...]:` prompt, it asks for the password again. Repeat.

### Expected behavior

Correct password unlocks the console and restores the normal prompt.

### Actual behavior

Password prompt repeats indefinitely. Screen fills with the lock message + `Wallet password:` lines. Wallet stays locked; I can't run commands.

In some runs it looks like it doesn't even wait for input (instant re-prompt). In others I type the password and still get bounced back to the same lock screen.

### Notes / what I dug into

Looking at the code, unlock is an infinite `while (1)` in `simple_wallet::check_for_inactivity_lock()` (`src/simplewallet/simplewallet.cpp`). It only breaks after `get_and_verify_password()` succeeds *and* (if background sync was started on lock) `stop_background_sync()` doesn't throw. Otherwise it loops and prints the lock banner again. So this is not a second 90s idle timeout — it's the same unlock loop failing repeatedly.

On Linux, password input goes through `getch()` / `getchar()` in `src/common/password.cpp`. If stdin hits EOF, `read_from_tty` returns false and there is no `clearerr(stdin)`, so a sticky EOF can make every unlock attempt fail instantly (`failed to read password`) and spin. That matches older reports with `screen` / no controlling tty.

Other failure modes that also look like "password doesn't work":

- `invalid password` (empty/garbled read after `cancel_input`, paste junk in raw mode, or wrong prompt when custom background-sync password is required)
- password verifies, then `stop_background_sync()` throws and the catch path just continues the loop (`Failed to unlock wallet: ...`)

Would be good to:

1. Not spin forever on EOF / failed read (backoff, clear EOF, or abort lock with a clear error / way out).
2. Make Ctrl+C / exit actually work from the lock password prompt.
3. Surface unlock failures clearly every time (including background-sync stop failures), and maybe skip starting background sync until unlock I/O is known-good.
4. Document that inactivity lock is Linux/macOS-only and is unsafe under detached `screen`/`tmux` without a real tty — or disable it automatically when stdin isn't a tty.

Happy to provide strace / exact binary version if useful.
